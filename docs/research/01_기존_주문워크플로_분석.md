### 상태 값과 전이 흐름 (파생 상태)
프론트 `orderStatus()`/`orderStatusKey()`가 우선순위로 파생: `cancelled > archived(출고 보관) > shipped(출고 확인) > softwareInspection(검수 완료) > produced(제작 완료) > preparing(준비 중) > waiting(제작 대기)`.

전이 규칙(서버 `do_PATCH`가 최종 강제, 위반 시 409 + 현재 order 반환):
```
제작 대기 → [preparing 체크: 담당자 클레임] 준비 중
        → [production 체크: preparing 자동 해제·기록] 제작 완료
        → [softwareInspection 체크: productionDone 필수] 검수 완료
        → [shipping 체크: production+inspection 모두 필수] 출고 확인
        → [출고 엑셀 생성(POST /api/export/shipped)] archivedAt 보관
```
- 역방향 가드: 출고 완료 주문은 제작/검수 해제 불가, 검수 완료 주문은 제작 해제 불가, **검수 해제 시 출고 상태 연쇄 해제**.
- 취소(`cancel`, 사유 필수 500자 제한)는 어느 단계든 가능(보관 주문 제외), 취소 시 preparing 초기화. `restoreCancel`로 복구.
- 준비/제작/검수/출고 각 단계는 체크 시 서버가 `worker = user["displayName"]`와 UTC 시각을 기록(클라이언트가 보낸 worker는 무시).

- 주문 테이블 한 행에 체크카드 4개: 준비 중 / 제작 완료 / SW 검수 / 출고 처리. 각 카드에 `담당자 · 시각` 부제(`formatDate`). 담당자 미지정 시 "작업자 미지정"/"검수 전"/"SW 검수 후 출고" 안내.
- 관리번호 textarea(한 줄 1개, 수량과 개수 일치 강제·중복 검사, Ctrl+Enter 저장), 드래프트는 `state.managementDrafts`에 보관해 재렌더에도 유지(`captureOrderInputState`/`restoreOrderInputState`).
- 일괄 처리 바: 다중 선택 후 준비/제작/검수/출고 일괄 PATCH(순차 루프, 개별 실패 집계).
- 상태 카드(대기/준비/제작/검수/출고 건수) = 필터 버튼 겸용. 처리 이력 타임라인은 상세 패널에 4단계로 표시.

## 6. 안정성: 잠금·백업·알려진 한계

### 잘 되어 있는 것
- 전역 `LOCK`(threading.Lock) 하나로 orders.json의 모든 읽기-수정-쓰기를 직렬화 → **단일 프로세스 내 lost-update 없음**. AUDIT_LOCK/SETUP_LOCK/LOGIN_LOCK/AuthStore lock 분리.
- 원자적 저장(tmp+fsync+replace), 일별 백업+14일 보존, 종료 스냅샷, watchdog 자동 재기동, ZIP 폭탄 제한, 업로드 크기·개수 제한, PBKDF2+compare_digest, 로그인 차단, HTML escape(`escapeHtml`) 일관 적용, 프론트 입력 중 폴링 스킵.
- 준비 중 클레임 충돌 409, 실패 시 서버 상태로 화면 복구 — 다인 동시 체크의 실질적 충돌 방지.

### 알려진 취약점/한계 (새 시스템에서 주의)
1. **GET 로그인 경로 존재** (`src/server.py:446-455`): `/?username=...&password=...` 쿼리스트링 인증 지원 → 자격증명이 액세스 로그·브라우저 히스토리에 남음. 제거 대상 1순위.
2. **관리번호 교차 중복검사 무력화 버그** (`src/server.py:753-760`): 다른 주문의 관리번호를 모아 `existing_numbers`를 만든 직후 `existing_numbers.clear()` 호출 → 중복 검사가 항상 통과. (같은 주문 내 중복 검사만 동작.)
3. **화면 낙관 반영 vs 5초 폴링 사이의 편집 lost-update**: 파일 쓰기는 직렬화되지만, A가 오래된 화면으로 "details" 수정을 저장하면 B의 변경을 필드 단위로 덮어씀(버전/ETag 없음). 체크박스는 409 가드가 있으나 상세수정·관리번호는 last-write-wins.
4. **다중 프로세스 가드 부재(Windows)**: 파일 잠금이 아닌 프로세스 내 Lock이므로 서버 2개가 뜨면 orders.json이 서로 덮임. Linux 배포는 flock을 쓰지만 Windows는 PID 파일 검사뿐(allow_reuse_address=False로 포트 충돌이 사실상의 가드).
5. **메모리 세션 + watchdog 재시작 조합**: 크래시 복구 시마다 전 직원 로그아웃.
6. **매 요청 전체 파일 파싱**: read_orders()가 요청마다 618KB JSON 파싱, PATCH 1건마다 전체 재직렬화. 399건 규모에선 문제없으나 확장 한계.
7. **audit.jsonl 무한 성장**(현재 982KB, 회전 없음). 알림이 audit 파생이라 회전 정책과 얽힘.
8. **전량 innerHTML 재렌더**: 5초마다 테이블 전체 재구축(입력 상태 캡처/복원 우회 장치 필요해짐), 주문 수 증가 시 스크롤 튐·성능 저하 위험.
9. **중복 정리 버튼은 미리보기 없이 즉시 삭제**(CODE_REVIEW_GUIDE 명시 운영주의).
10. 실데이터 품질: channel에 `450000`, `660000` 같은 금액 오염 값 2건 존재 — 임포터 예외 케이스 방증.
11. CSRF 토큰 없음(SameSite=Lax + JSON Content-Type 프리플라이트로 부분 완화), HTTPS 없음(LAN 전제).

## 7. 이식 판단: 그대로 가져갈 것 vs 재설계할 것

### 그대로 이식할 가치가 높은 것
1. **PATCH action 기반 상태머신 + 서버 최종 검증 패턴** (`do_PATCH` 전체): preparing→production→softwareInspection→shipping 순서 강제, 역방향 가드, 검수 해제 시 출고 연쇄 해제, 409 시 `{error, order}` 반환으로 프론트 자동 복구. 이 계약(에러에 최신 주문 동봉)이 폴링 기반 동기화의 핵심.
2. **준비 담당자 클레임 규칙**: 체크한 사람=담당자, 타인 점유 시 체크/해제 모두 409 — 별도 지정 UI 없이 동시작업 충돌을 해결하는 검증된 최소 설계.
3. **「불리언+By+At」 3필드 상태 세트** 데이터 모델: 단계별 책임자·시각 추적, 처리 이력 타임라인, 작업자별 검색이 전부 이 구조에서 파생.
4. **3계층 폴링 + 입력 중 스킵 + 포커스 강제갱신** (`refreshVisibleData`/`isEditingOrderInput`/focus·visibilitychange): 로컬 LAN 소규모 팀에는 WebSocket 없이 충분함이 실증된 조합. 주기(5/10/15초)와 드래프트 보존(`managementDrafts`, `captureOrderInputState`) 장치까지 세트로 이식 권장.
5. **알림 = 감사로그 파생** 설계(`read_notifications` + `pollNotifications`의 key/fingerprint 이중 dedupe): 별도 알림 저장소 없이 "누가 무엇을 했는지" 토스트/알림센터 제공.
6. **중복 판정 모듈**(`src/orders/dedupe.py` 전체): 다층 키(실번호/내용지문/쿠팡교차), 상태 보존 병합, pendingShippingUpdate 승인 흐름 — 순수 함수라 그대로 재사용 가능.
7. **원자적 저장 + 일별 백업 + 종료 스냅샷**(`write_orders`/`backup_file`/`write_shutdown_backup`) 및 **watchdog/24x7 스케줄러 스크립트 세트**.
8. **채널별 엑셀 헤더 매핑 사전**(`_first` 후보 목록들)과 헤더 자동 감지, 주문수집 다행 그룹핑 로직 — 실운영에서 다듬어진 도메인 지식.
9. 역할 매트릭스·developer 서열 가드·마지막 owner 보호·로그인 차단 로직(`src/auth.py`, `_update_user`).

### 재설계해야 할 것
1. **GET 쿼리스트링 로그인 제거** (보안).
2. **관리번호 중복검사 버그 수정**: `existing_numbers.clear()` 삭제(또는 정책 확정) — 이식 시 그대로 복사하면 안 됨.
3. **저장 계층**: 주문 수 증가 대비 SQLite(WAL) 등으로 교체 권장. 최소한 파일 수준 잠금(msvcrt/portalocker)으로 다중 프로세스 가드 추가. JSON을 유지한다면 주문별 버전 필드(`updatedAt` 비교) 기반 낙관적 잠금을 details/관리번호 수정에 도입해 last-write-wins 제거.
4. **세션 영속화**: 파일/DB 저장으로 watchdog 재시작 시 로그아웃 문제 해결.
5. **렌더링**: 전량 innerHTML 재구축 대신 행 단위 diff 갱신(또는 경량 프레임워크). 주문 수백 건 이상이면 필수.
6. **실시간성 강화 여지**: 5초 폴링 유지가 기본값으로 무난하나, 새 시스템에서 "실시간 체크 동기화"를 더 촘촘히 원하면 SSE(표준 라이브러리로 구현 가능)로 변경 이벤트 push + 폴링 폴백 구조 검토. 전체 목록 재전송 대신 `updatedAt > since` 증분 API 추가.
7. **audit.jsonl 회전/보존 정책** 및 알림 API의 분리(파생이 아닌 명시 이벤트 스토어).
8. **중복 정리 미리보기** 단계 추가(현재는 즉시 삭제).
9. 임포터의 channel 오염(`450000` 등) 방지 검증 추가, .xls 변환의 LibreOffice 의존은 새 환경 요건에 맞춰 재검토.
10. CSRF 토큰, (외부 노출 시) HTTPS/리버스 프록시.
