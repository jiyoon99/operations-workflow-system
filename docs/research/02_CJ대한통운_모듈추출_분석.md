E:/rental-system/app.py의 CJ대한통운 연동은 구세대(cj_*, PA-P 게이트웨이 추정 스펙·사실상 데드코드)와 신세대(cj2_*, 표준 API V3.9.4 정식 클라이언트)의 2계층으로, 재사용 대상은 cj2_* 약 40개 함수(토큰 ReqOneDayToken·채번 ReqInvcNo·접수 RegBook·취소 CnclBook·추적 ReqOneGdsTrc·주소정제 ReqAddrRfnSm + 동결 레이아웃 운송장 PDF 렌더러 cj2_waybill_pdf)입니다. 클라이언트 코어는 이미 `cj: dict` 설정을 인자로 받는 순수 함수형이라 추출이 쉽고, 운송장 PDF는 reportlab+말군고딕(KOR/KORB)+code128만 있으면 외부 이미지 없이 동작하므로 마스킹/포맷 헬퍼 4종과 폰트 등록 코드를 함께 그대로 복사하면 됩니다(레이아웃 동결 — 수정 금지). 발급 데이터는 SQLite KV 'waybills' 테이블에 WB-일자-NN 키로 라벨 스냅샷과 함께 기록되며, whole-dict 재저장 구조 탓에 락+머지저장 패턴이 필수입니다. 네이버 스마트스토어 연동(bcrypt 서명 OAuth·주문수집·레이트리밋 쿨다운)도 별도로 존재하며, 새 시스템에서는 단일파일 모놀리스·무인증 라우트·전체 덮어쓰기 저장의 3대 구조 문제를 블루프린트 분리·전역 인증 게이트·키 단위 upsert로 예방할 것을 제안합니다.

## 2. 인증/설정

### 설정 위치와 키
설정은 **SQLite DB에 저장**(`load_cfg`→`db_get_cfg`, 2960)되며 `config.json`은 레거시 스냅샷입니다(실파일의 cj 섹션에는 구키만 존재: apiKeyWaybill/apiKeyRecall/customerCode=30516776/sender* — 신키 env/cust_id/biz_reg_num은 DB 쪽 설정에 있음). `DEFAULT_CFG['cj']`(2902~2920) 기준 키:

**신 체계(cj2_*, 재사용 대상)**
- `env`: 'dev'(개발서버·실배송X) | 'prod'(운영·실배송)
- `cust_id`: 고객사 코드(미입력 시 `customerCode`=30516776 재사용)
- `biz_reg_num`: 사업자등록번호(토큰 발급 필수)
- `armed`: **운영 실발급 잠금 토글** — env=prod AND armed=True여야 실발급(`_cj2_prod_locked`, 9003 → HTTP 423). 이중 안전장치
- `sender{}` / `pickup{}`: 출고지/고정 회수지 {name,tel,zip,addr,addr_detail}
- `perBoxFee`: 박스당 택배비(다매 자동계산·배송비 반영용)
- `label_ox/oy/sc/kx/ky/rot/media/rdir`: 운송장 인쇄 정렬 보정값(`_cj_label_offset`, 9551)

**구 체계(레거시, 추출 불필요)**: `apiKey/apiKeyWaybill/apiKeyRecall/apiKeyTracking`, `baseUrl`, `tokenEndpoint/waybillEndpoint/recallEndpoint/trackingEndpoint`, `senderName/senderTel/senderZipcode/senderAddress/senderAddressDetail`

### 토큰 갱신 방식
1. `cj2_token`(8342): POST `{env호스트}/ReqOneDayToken`, body `{DATA:{CUST_ID, BIZ_REG_NUM(숫자만)}}` → `TOKEN_NUM`(24h 유효, `TOKEN_EXPRTN_DTM` 파싱)
2. 프로세스 메모리 캐시 `_cj2_token_cache`(cust_id별), **만료 30분 전 자동 재발급**
3. `cj2_call`에서 **HTTP 401 시 강제 재발급 후 1회 재시도**
4. 호출 인증 = 헤더 `CJ-Gateway-APIKey: {토큰}` + body `DATA.TOKEN_NUM` 이중 전달
5. cj 섹션은 `_SECRET_CFG_SECTIONS`(3418)에 포함 — 설정 API 응답에서 마스킹됨

```
→ cj2_addr_refine(1회) → [매수만큼 루프: cj2_new_invoice 채번 → cj2_reg_book(01)]
→ _cj2_label(라벨 스냅샷) → _cj2_record_waybill(락+재읽기 → waybills 저장)
→ 렌탈 현황 갱신: tracking_no, history, 자산 holding→rented, fee_adjust(미수/조정매출)
   — _save_rental_merge(rid만 머지 저장: CJ I/O 중 다른 편집 유실 방지)
```
**waybills 레코드 스키마**(`_cj2_record_waybill`, 8534): 키=`WB-YYYYMMDD-NN`, 필드 = `type`(forward/exchange/recall ← cj_kind 매핑), `cj_kind`, `invoice_no`, `status`(issued/failed/…/delivered/canceled), `rental_id`/`order_id`, 고객 연락처·주소, `items`, `scheduled_date`, `label`(출력 스냅샷), `cj_response`(원본 응답), `cust_use_no`, `ori_invc_no`, `cj_rcpt_ymd`, `box_qty`, `pickup_date`, `rebook_of`, `cj_booking_canceled`, `cj_stage_cd/nm/at/bran` 등. 저장소는 SQLite KV 'waybills'. 별도로 구세대 `shippings`(주문ID→배송정보, 655) 저장소와 렌탈의 `tracking_no` 필드가 공존하며, `/api/waybills` 목록이 이들을 읽기전용 합성(_synthetic)으로 병합 표시.

### 회수(반품) 흐름
- 보내는분=고객(물건 위치), 받는분=고정 회수지(`_cj2_pickup`)
- **INVC_NO 없이 접수**(CJ가 기사 출력 시 채번) — waybills에는 `invoice_no:''`로 기록, 나중에 번호가 채워지면 추적 대상化
- `cust_use_no`는 `{rid}-R{HHMMSS}` 유일화(같은 날 재접수 ORA-00001 회피), `cj_rcpt_ymd`=실접수일(오늘) 저장 → CnclBook PK
- `COLCT_EXPCT_YMD`(수거희망일)는 CJ '현재 사용 안함' 필드 — 내부 표시용(scheduled_date)으로만 의미
- 회수 완료(추적 91 또는 계약종료 액션) → `_auto_release_assets_for_order`로 자산 가용 복원

### 취소/재접수
- 취소 PK = (RCPT_YMD, CUST_USE_NO, 접수구분). 회수 건은 `cj_rcpt_ymd` 우선 사용(수거희망일 오인 방지)
- 로컬 취소는 락 안에서 status='canceled' + `cj_booking_canceled` 플래그
- rebook: 취소→새 채번→`-RB` suffix 재접수→원 송장 무효화→rentals.tracking_no/shippings 동기화

### 추적 동기화
3시간 데몬(`_cj_track_scheduler`) + 수동(`/api/cj2/track-sync`) → `cj_stage_*` 갱신, 91=delivered 처리. **변경 wid만 머지 저장**(`_save_waybill_changes`)으로 동시 취소 보존.

## 5. 네이버 스마트스토어 연동 — 존재함

- 설정: `cfg['naver']` = `clientId`, `clientSecret` (Naver Commerce API)
- **인증**(3532 테스트, 3766 실사용): timestamp(밀리초, -3초 스큐 보정) → `bcrypt.hashpw(f"{clientId}_{timestamp}", salt=clientSecret)` → base64 = `client_secret_sign` → POST `https://api.commerce.naver.com/external/v1/oauth2/token` (type=SELF) → Bearer 토큰
- **주문 수집** `_fetch_naver_orders`(3754): 키 미설정 시 시뮬레이션(MOCK) 폴백. `GET /external/v1/pay-order/seller/product-orders`를 24시간 청크로 최대 90일, 직렬+200ms 간격(초당 5회 제한의 안전 마진), 상태 enum은 PAYED/DELIVERING/DELIVERED/PURCHASE_DECIDED만(그 외는 400)
- **레이트리밋 방어**: 응답 헤더 `GNCP-GW-RateLimit-Remaining` 추적→잔여 2 이하 사전 대기, 429 시 5분 쿨다운(`_naver_cooldown_until`, 4023) — 자동조회는 캐시만, 수동 fresh=1은 무시 가능
- **매핑** `naver_map`(3262): product-order → 내부 공통 주문 형식(주문자 ordererName/Tel, 수령인 shippingAddress{name,tel1,zipCode,baseAddress,detailedAddress}, orderUrl/productUrl 생성). 택배비 누락 매핑버그 소급정정 라우트 `/api/revenues/recalc-naver`(11231)
- 주문 캐시 `_orders_cache`(4019) + 고도몰(`Order_Search.php` XML)과 병렬 수집(4393) 후 합산
- CJ 출고 시 이 주문 캐시(`_order_from_cache`, 4025)에서 수령인/주소를 폴백으로 씀 — **CJ 모듈과 스마트스토어 모듈의 접점은 이 '주문 캐시 조회' 하나**로 좁혀져 있어 분리 용이

## 6. 새 프로젝트 모듈 추출 제안

cj2_* 코어는 이미 `cj: dict`를 인자로 받는 순수 함수 스타일이라 결합도가 낮습니다. 추출 순서(의존성 적은 것부터):

**1) `cj/client.py` — API 클라이언트 (의존: requests, re, datetime만)**
`CJ2_HOSTS`, `_cj2_token_cache`, `cj2_token`, `cj2_call`, `cj2_new_invoice`, `cj2_addr_refine`, `cj2_track`, `cj2_reg_book`, `_cj2_phone`, `_cj2_party`, `_cj2_cust`, `_cj2_base`. `log()` 호출만 표준 logging으로 치환. **반품 INVC_NO 하드가드·전화분할 특례·401 재시도는 그대로 유지**(전부 실사고 기반 수정).

**2) `cj/waybill_pdf.py` — 동결 렌더러 (의존: reportlab)**
`cj2_waybill_pdf` 본문 그대로 + 3절의 의존 목록 전부. 골든 샘플 PDF(`_cj2_sample_label` 렌더 결과)를 저장해 두고 복사 후 바이트/픽셀 비교로 동일성 검증 권장. 보정값은 함수 파라미터로 이미 분리돼 있어 `_cj_label_offset`만 Flask request 대신 설정 dict를 받게 재작성.

**3) `cj/label.py` — 라벨 데이터**
`_cj2_label`, `_cj2_sync_label_from_record`, `_cj2_sample_label`. 라벨 dict 스키마가 계약(contract)이므로 dataclass/TypedDict로 명세화 권장.

**4) `cj/store.py` — 저장 어댑터 (포트/어댑터 패턴)**
`load_waybills/save_waybills/next_waybill_id/_waybills_write_lock/_save_waybill_changes`를 인터페이스(WaybillRepo)로 추상화. 새 시스템 DB가 무엇이든 **키 단위 upsert**로 구현하면 rental-system의 whole-dict 재저장(DELETE 전체+INSERT 전체, db_save_kv 352)이 강제했던 락+머지저장 곡예가 필요 없어짐. `_cj2_record_waybill`은 여기로 이동하되 렌탈 필드 대신 '주문' 필드로 일반화.

**5) `cj/routes.py` — Flask Blueprint**
ship/return/cancel/rebook/track/label-pdf 핸들러를 얇게 이식. 렌탈 도메인 의존부(`_cj2_resolve_rid`, `_ensure_persistent_rental`, 자산 전환, fee_adjust 미수/매출 반영, `_order_from_cache`)는 하프북 도메인에 맞는 **주문 프로바이더 인터페이스**(주문ID→수령인/품목/전화 폴백)로 치환. `_cj2_prod_locked`(env+armed 이중 잠금)·전화 필수 가드·cust_use_no 유일화·ORA-00001 안내는 반드시 이식.

**6) `cj/tracker.py` — 추적 스케줄러**
`_cj_sync_one_waybill`, `_cj_track_scheduler`, track-sync. '배송완료 시 콜백'(rental-system에선 자산 복원)을 주입식으로. 과호출 방지 규칙(3h 주기·종결 제외·21일 컷·0.3s 지연·dev 스킵)은 CJ 가이드 기반이므로 유지.

**제외 권장**: 구세대 `cj_*` 전체(8131~8296, `/api/shipping/cj-create` 9989, 회수 시뮬 22540 블록), `cj2_exchange`(데드코드 판정 — 필요 시 ship+return 조합으로 재구현), `/api/cj2/test-labels-pdf`(테스트 전용).

**설정 대체**: `load_cfg()` 전역 대신 생성자 주입(CJConfig dataclass: env/cust_id/biz_reg_num/armed/sender/pickup/perBoxFee/label_*). 키 이름을 유지하면 기존 설정 이관이 쉬움. 시크릿은 설정 파일 평문 대신 환경변수/시크릿 스토어 권장(현 config.json에는 타 서비스 비밀번호가 평문 존재).

## 7. 새 시스템에서 반복하지 말아야 할 구조적 교훈

1. **단일파일 모놀리스 금지**: 1.3MB app.py 안에 클라이언트·렌더러·스케줄러·라우트·도메인이 뒤섞여 "cj 모듈을 별도 분리하는 게 깔끔하나 현 구조 유지"(22559)라는 주석까지 있음. 처음부터 blueprint+패키지로.
2. **전역 인증 게이트 부재**: 2026-07 감사에서 무가드 라우트 98개 확정. CJ 쪽에도 `/api/cj2/test`, `/api/cj2/sample-label-pdf`, `/api/cj2/test-labels-pdf`, `/api/shippings`(GET), `/api/shipping/cj-create`가 무인증. 새 시스템은 **`before_request` 전역 게이트 + 명시적 공개 allowlist** 방식으로(라우트마다 데코레이터 붙이는 opt-in 방식은 누락이 구조적으로 발생).
3. **whole-dict 저장 → lost-update 사고**: waybills 누락 사고(2026-07-15), 3건발송·1건기록 사고 등 전부 '전체 읽고 전체 덮어쓰기' 탓. 락(`_waybills_write_lock`)과 머지저장(`_save_waybill_changes`)은 사후 봉합임. 새 시스템은 **레코드 단위 upsert/트랜잭션**을 기본으로.
4. **스냅샷 이중화 주의**: 라벨(출력 스냅샷)과 송장 기록이 분리돼 수정 시 desync 발생(2026-07-15 대표 발견 → `_cj2_sync_label_from_record` 봉합). 새 설계에서는 라벨을 출력 시점에 기록에서 파생 생성하고, 스냅샷이 필요한 필드(분류코드 등 CJ 응답)만 저장.
5. **실발급 안전장치는 유지·강화**: env(dev/prod)+armed 이중 토글, 423 잠금 응답, 전화번호 사전 차단(게이트웨이 'S'≠실접수), 반품 INVC_NO 공란 규칙, cust_use_no 유일화 — 전부 실사고/CJ 개발팀 회신으로 얻은 규칙이므로 새 시스템에 그대로 이식. 검증은 격리 프로브(부수효과 저장소 전부 모킹)로만.
6. **운송장 렌더러 격리**: cj2_waybill_pdf는 동결 상태이므로 독립 모듈+골든 샘플 테스트로 보호하고, 위치 보정은 코드가 아닌 설정값(label_*)으로만 — 기존 원칙 그대로.
7. **시크릿 관리**: config.json에 타 서비스 자격증명이 평문으로 존재. 새 시스템은 환경변수/OS 자격증명 저장소 사용, 설정 API 응답 마스킹(_SECRET_CFG_SECTIONS 패턴)은 유지.
8. **백그라운드 스레드**: 데몬 스레드 방식은 재기동 시 유실·중복 실행 위험. 새 시스템에서는 스케줄러를 단일 진입점으로 모으고 멱등성(변경분만 저장, 터미널 상태 재조회 금지)을 계약으로 명시.
