### 확정된 대표 결정 (2026-07-28)
1. **CJ대한통운은 기존 고객코드(30516776) 사용** — 이 코드는 **하프전자 주식회사 명의**의 고객코드(아서렌탈 명의가 아님)로, RMS와 HMS가 동일 코드를 공용. 설정에 코드 입력란은 유지(향후 분리 대비)
2. **RMS와 분리 운영**(별도 포트 5100). 개발이 어느 정도 끝나면 RMS·HMS 모두 각각 다른 PC로 이전 예정 → **폴더 복사만으로 이전 가능하도록 경로 독립적으로 구성**
3. **기존 order-workflow의 로그인/역할 체계(owner/developer/… 6종)는 폐기.** 모든 사용자는 HMS 통합 계정으로 관리 — 대표가 설정 화면에서 직접 계정 생성·권한 부여, 모든 이력은 HMS 계정 기준으로 기록
4. **카테고리·담당자 구성은 대표가 설정 화면에서 직접 관리** (사용자별 권한 + 카테고리 스코프 UI 제공)
5. **(2026-07-28 추가) 몰 API 키 신청은 후순위** — 시스템이 어느 정도 구축된 후 주문수집 테스트 시점에 진행. 그 전까지 주문은 엑셀 임포트로 운영
6. **(2026-07-28 추가) 자산번호 규칙**: 기본 자동 발번 `YYYYMMDD+0001`(당일 순번), 단 **기존 TMS 자산번호를 따라와야 하는 경우가 있어 수정 가능해야 함**. 자산번호 기준 이력관리가 최우선 요구사항
7. **(2026-07-28 추가) 송장 선출력 워크플로**: QC(세팅) 완료 → 출고팀(포장) 인계 **전에** 송장을 먼저 출력. 송장의 상품명 영역에 ①쇼핑몰/제품 코드(모델명·상품명) ②출고 자산번호 ③추가옵션을 표기해 출고 구성품 대조 검증이 가능해야 함(운송장 레이아웃은 동결 — 상품명 텍스트 구성으로 구현)
8. **(2026-07-28 추가) TMS 매입 구조 반영** — 기존 TMS(tms.jd-soft.kr, 하프전자그룹) 매입 화면 확인 후 결정:
   - **가입고 2단계 도입**: 가입고(V전표) → 입고확인 → 매입(P전표). 폼 구조는 동일, 진행상태로 구분
   - **등급과 상태 분리**: 품질등급 13종(미정/NU/S+A/S+S/SS/SA/AS/AA/SB/AB/A급/B급/C급)은 등급으로,
     수리·A/S·불량·도색대기는 **자산 상태**로 관리(TMS는 한 목록에 섞여 있으나 재고 집계 정확도를 위해 분리)
   - **관리번호 = YYMMDD-NNNN**(TMS 형식과 동일, 예 260719-0027). 수동 지정도 계속 허용
   - **노트북 스펙 필드 신설**: CPU / 그래픽 / RAM / SSD / 인치 / 배터리효율 / 충전기유무 + 보관위치 + 판매가
   - 매입 헤더 확장: 전표번호·매입구분·매입채널·수령방식·신청자·부가세·수수료·배송비(착불)·송장번호·납부확인(완납/미지급)
   - **엑셀 이관 기능**: TMS 자산 데이터를 엑셀로 받아 일괄 등록(관리번호·스펙 그대로)
   - 제외: 순이익액(판매 단계에서 계산), SCAN·매입반품 등 미사용 항목
9. **(2026-07-28 추가) 권한 = 메뉴 단위 접근 제어**: 대표가 말한 "카테고리 권한"은 제품 분류가 아니라
   **메뉴 접근 권한**이다. 사용자 관리에서 사람마다 쓸 메뉴(매입/주문관리/셋팅/배송/A-S/설정)를 체크하면

   설정의 [카테고리] 탭은 제거하고 제품 분류 관리는 매입 > [거래처 / 분류]로 옮김.
10. **(2026-07-28 추가) API 관리 탭**: 설정의 [배송/CJ대한통운]을 **[API 관리]**로 바꾸고

   비밀 항목은 저장 후 마스킹되며 마스크를 그대로 저장하면 기존 값이 유지된다.
11. **(2026-07-28 추가) 스펙 자동완성**: CPU·GPU·RAM·SSD 등에 2010년 이후 표기 카탈로그(약 2,360개)를 넣고
   입력 시 부분일치 필터로 제시. 카탈로그에 없는 값도 자유 입력 가능하며, 한 번 쓰면 '사용 중'으로 후보에 축적된다.

## 1. 목표와 범위

**한 문장 요약**: 매입된 노트북을 **자산번호 1대 단위**로 입고→상품화(준비/QC)→판매→출고(CJ 송장 자동출력)→회수까지 추적하고, 입점 쇼핑몰 8곳의 주문을 API로 자동 수집해 주문↔자산↔송장↔고객이 끊김 없이 매칭되는 시스템.

### 포함 범위
1. **주문관리**: 쇼핑몰 8곳(고도몰5·쿠팡·카카오쇼핑·토스쇼핑·11번가·롯데온·ESM·테무) API 주문수집 + 수기(전화/방문) 주문 + 엑셀 임포트(과도기/폴백)
2. **택배 발송·회수**: rental-system의 CJ대한통운 표준 API(V3.9.4) 모듈 재사용 — 송장 발급·PDF 자동출력·회수예약·추적
3. **매입 관리**: 거래처 관리, 거래처별 입고날짜·입고금액, 자산번호별 특이사항·수리비용
4. **준비/QC 워크플로**: 기존 order-workflow 시스템의 "누가 준비했고 누가 검수했는지" 실시간 체크·동기화 기능 이식
5. **권한**: 카테고리별 담당자 접근 제어 (역할 + 카테고리 스코프)

### 제외 범위 (이번 단계 아님)
- 아서렌탈 RMS와의 통합(별도 시스템으로 운영, CJ 모듈 코드만 공유)
- 쇼핑몰 상품등록/가격관리 API(주문·송장·클레임만)
- 회계/세금계산서 연동

## 2. 제1원칙: 안정성

아서렌탈 RMS 운영에서 실제 사고로 배운 교훈을 설계 원칙으로 승격한다. **기능보다 원칙이 우선한다.**

| # | 원칙 | 배경(실사고/감사) |
|---|---|---|
| 1 | **단일 DB 원본**: SQLite(WAL) + 트랜잭션 + 레코드 단위 upsert. "전체 읽고 전체 덮어쓰기" 금지 | waybills 유실(2026-07-15), 3건발송·1건기록 lost-update 사고 |
| 2 | **전역 인증 게이트**: `before_request` 전역 차단 + 명시적 공개 allowlist. 라우트별 데코레이터(opt-in) 방식 금지 | RMS 감사에서 무가드 라우트 98개 발견 |
| 3 | **외부 API 호출은 이중 잠금**: env(dev/prod) × armed 토글. 미설정 시 시뮬레이션 모드가 기본 | CJ armed 잠금(HTTP 423) 패턴 검증됨 |
| 4 | **부수효과 검증은 격리 프로브로만**: 실계정 쓰기 API 검증 호출 금지, 저장소 전부 모킹 후 실행 전후 불변 확인 | 라이브 DB 오염 사고(2026-07-15) |
| 5 | **중복 방지 가드 선제 적용**: 발송 inflight/dup 가드, 주문 다층 중복키, 몰별 송장 중복 규칙 준수 | 계약 3건 발송·1건 기록 사고, 쿠팡 6개월 중복송장 에러 |
| 6 | **원자적 저장 + 일별 백업 + 종료 스냅샷 + watchdog**: 기존 시스템에서 검증된 세트 그대로 | order-workflow에서 실증 |
| 7 | **감사로그 전면화**: 모든 쓰기 작업에 누가/언제/무엇을 append-only 기록 + 회전 정책 | audit.jsonl 무한 성장 한계 보완 |
| 8 | **시크릿 분리**: API 키는 DB 암호화 저장 또는 환경변수, 설정 API 응답 마스킹 | RMS config.json에 타 서비스 비밀번호 평문 존재 |
| 9 | **낙관적 잠금**: 상세 수정에 버전(updatedAt) 비교 — last-write-wins 금지 | order-workflow의 편집 덮어쓰기 한계 |
| 10 | **단일 프로세스 강제**: 앱 락 파일 + 포트 점유 확인(Windows에서 서버 이중 기동 방지) | order-workflow의 다중 프로세스 가드 부재 |

## 3. 아키텍처

### 기술 스택
| 영역 | 선택 | 이유 |
|---|---|---|
| 백엔드 | Python 3.12 + Flask (**app factory + Blueprint 패키지 구조**) | CJ 모듈·엑셀 임포터가 Python이라 재사용 직결. 단일파일 모놀리스(RMS 1.3MB app.py)는 금지 |
| DB | **SQLite (WAL 모드)** 단일 파일 | 로컬 서버 PC 운영, 트랜잭션·동시 읽기, 백업 간단. JSON 파일 저장(order-workflow 방식)은 확장 한계로 채택 안 함 |
| 프론트 | 정적 HTML + 바닐라 JS (행 단위 갱신) | 기존 팀 익숙함, 빌드 불필요. 전량 innerHTML 재렌더는 금지 |
| 실시간 동기화 | **폴링 3계층**(주문 5초·알림 10초·헬스 15초) + 입력중 스킵 + 포커스 강제갱신 | order-workflow에서 LAN 다인 사용 실증. `updatedAt > since` 증분 API로 부하 절감 |
| PDF | reportlab (CJ 운송장 동결 렌더러 그대로) | 레이아웃 동결 — 바이트 단위 복사 |
| 운영 | Windows 서버 PC, watchdog + 작업 스케줄러 24x7, 포트 **5100**(RMS 5000과 분리) | 기존 운영 패턴 유지 |

│   └── settings/            # 설정 화면: 몰별 자격증명(마스킹)·CJ·백업
├── static/ + templates/
├── tests/                   # unittest — 기존 41개 테스트 자산 이식 + 신규

### 저장소 핵심 규칙
- 모든 쓰기는 `db.py`의 트랜잭션 헬퍼 경유(레코드 단위 UPDATE/INSERT).
- 일별 백업(14일 보존) + 종료 스냅샷 + 수동 백업 버튼.
- 감사로그는 SQLite 테이블(월 단위 파티션 뷰) — jsonl 무한 성장 문제 해소.

## 5. 권한 모델 — HMS 통합 계정 (2026-07-28 대표 지시 반영)

기존 order-workflow의 역할 6종(owner/developer/as_manager/sales_manager/md/worker)은 **이식하지 않고 폐기한다.** 대신:

- **HMS 통합 계정**: 모든 사용자는 HMS에서 생성한 계정으로 로그인. 최초 기동 시 1회 관리자(setup) 생성, 이후 계정은 관리자가 발급
- **사용자별 기능 권한 토글**: 고정 역할 대신 기능 단위 권한(주문 조회 / 준비·QC 체크 / 주문 등록·수정 / 가져오기 / 취소 / 출고·송장 / 매입·자산 / 송장관리 / 통계 / 감사로그 / 설정 / 사용자관리)을 대표가 설정 화면에서 사용자별로 직접 켜고 끔
- **카테고리 스코프**: 사용자별 접근 카테고리 지정(또는 전체). 스코프 밖 데이터는 **서버 쿼리 레벨에서 제외**(프론트 숨김만으로 처리 금지)
- **관리자(is_admin)**: 전 권한 + 사용자/권한 관리. 마지막 관리자 보호 가드(비활성화·강등 불가). 관리자 지정/해제는 관리자만 가능
- **이력 통일**: 준비/QC 체크 담당자, 자산 이벤트, 감사로그 등 모든 이력은 HMS 계정(표시이름) 기준으로 기록
- 세션 DB 영속(재시작 시 로그아웃 없음), PBKDF2 해시, 로그인 실패 5회 차단
- QC 워크플로 이식 시 필수 수정: ① GET 쿼리스트링 로그인 제거, ② 관리번호 중복검사 무력화 버그 수정 — 로그인·권한 검사는 전부 HMS 게이트로 대체

## 6. 핵심 업무 흐름

### ① 매입 → 입고
거래처 선택 → 입고배치 등록(입고일·금액) → 자산 개별 등록(자산번호 채번, 모델·등급·특이사항) → 상태 '입고'. (향후: 아서렌탈 자산등록 OCR 자동화 연계 검토)

### ② 상품화 (준비/QC — 기존 기능 이식)
- 단계: **준비 중 → 제작 완료 → SW 검수 → 출고 확인** (서버 강제 상태머신, 역방향 가드, 검수 해제 시 출고 연쇄 해제)
- **담당자 클레임**: 체크한 사람 = 담당자. 타인이 점유한 단계는 체크/해제 모두 409 거부 → 충돌 없는 동시작업
- 실시간 동기화: 5초 폴링 + 409 시 서버 최신 상태로 화면 자동 복구 + 알림 토스트(감사로그 파생)
- 각 단계에 담당자·시각 영구 기록 → "누가 준비했고 누가 검수했는지" 조회·통계

### ③ 판매 → 매칭 → 출고 (핵심 자동화 체인)
```
몰 주문 자동수집(폴링) → 주문보드 신규 표시 → 담당자가 자산번호 매칭(스캔/검색)
→ QC 완료 검증 게이트 통과 → [출고 버튼 1회] →
   CJ 송장 채번·접수 → 운송장 PDF 자동 출력 → 몰에 송장번호 자동 전송(발송처리)
→ 자산 상태 '출고완료' + 주문·고객·송장·자산 4자 매칭 완료
```
- 발송 전 자동 확인: 취소요청 유무(쿠팡 RU 등 몰별 출고중지 확인), 전화번호 필수 가드, 중복발송 inflight 가드
- 몰 송장전송 실패 시 재시도 큐 + 실패 목록 화면(방치 시 자동취소되는 몰이 있어 알림 필수)

### ④ 회수 (반품/교환)
클레임 API 폴링으로 반품/교환 감지 → CJ 회수예약(기존 모듈: 송장번호 공란 접수, 고객→회수지) → 회수 완료 시 자산 '재입고(정비중)' 복귀 → 재상품화

> - **A/S**: 접수→회수→수리→반송, 자산 이력 연동, 무상 건은 수리비를 자산 원가에 반영(유상은 차단)
> - 테스트 98개 통과

### Phase 1 — 매입/자산 관리
