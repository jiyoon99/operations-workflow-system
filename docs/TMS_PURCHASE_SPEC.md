## 1. 매입등록 화면 — 2단 구조

TMS 매입은 **전표(헤더) 1건 + 매입상세(자산) N건**이 한 화면에서 처리된다.
상세를 `[상세추가]`로 쌓은 뒤 저장하면 전표와 자산이 함께 생성된다.

## 2. 채번 규칙 (실데이터로 확인)

- **전표번호**: `P260730-001`, `P250117-002` … → `P{YYMMDD}-{3자리}`
  - 가입고는 `V250402-001` → `V{YYMMDD}-{3자리}`
  - 판매는 `S260730-001`, A/S는 `A250410-001`
- **관리번호(자산)**: `260730-0009`, `250107-0068` → `{YYMMDD}-{4자리}`
  - 재고내역 14,969건 전수 확인: **중복 0, 전부 고유**

## 4. OWS 개발 시 반드시 지킬 것

1. **전표 1 : 자산 N** 관계를 깨지 않는다(TMS와 동일).
2. 전표번호와 관리번호는 **규칙이 다르다**(3자리 vs 4자리, 접두 유무).
3. 관리번호는 **수동 지정도 허용**해야 한다(TMS 이관분을 그대로 받기 위해).
4. **매입가는 자산 단위**로 들어간다 — 전표 총액만 저장하면 마진 계산이 틀어진다.
5. 진행상태·재고상태는 **파생값**이지 입력값이 아니다.

## 5. 실데이터 14,966건 전수 분석으로 확인된 것 (2026-07-30)

### 5-1. 전표 1 : 자산 N 이 사실이다
전표 헤더의 `매입수량` = 그 전표에 딸린 자산 행 수.
**465건 중 462건 일치**, 불일치 3건은 헤더 수량이 0인 취소성 전표(P241123-017 등).

### 5-2. 관리번호는 `YYMMDD-NNNN` 100% 준수
14,966건 **전부** 형식 일치, 예외 0건.

### 5-3. ★번호는 재사용하지 않는다 (OWS 구현 검증 완료)
날짜별 순번을 보면 **291일은 연속, 152일은 중간이 비어 있다**(취소·삭제 흔적).
즉 지워진 번호를 당겨 쓰지 않는다 → 채번은 **MAX+1**이어야 하고 COUNT+1이면 틀린다.

OWS `next_asset_no()` / `next_slip_no()` 모두 `MAX(...)+1` 방식 → **TMS와 일치함**(2026-07-30 확인).

### 5-4. 매입가는 자산 단위
자산행 14,966건 중 **13,931건에 매입가 보유**. 전표 총액이 아니라 대당 금액이다.

## 6. 아직 미확인 (필요 시 추가 조사)

- 매입상세의 `매입수`를 2 이상으로 넣었을 때 자산이 N건 생성되며 관리번호가 각각 붙는지
  (실데이터상 관리번호는 전부 고유하므로 N건 생성이 유력하나 화면 조작으로 확인은 안 함)
- SCAN 드롭다운의 정확한 동작
- 반품/취소 시 자산 상태 변화 규칙
